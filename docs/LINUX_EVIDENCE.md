# Linux container evidence

Verified 12 September 2026 using Docker Desktop 4.90.0 / Linux AMD64 engine 29.7.2 on a Windows host. This is actual Linux process/media execution, not Linux desktop/clipboard verification.

A separate Linux x64 Electron archive now exists with a bundled standalone backend. Its extracted backend passed in a minimal Debian image without global Node/FFmpeg/fonts; exact archive hashes and limits are recorded in [Linux package evidence](LINUX_PACKAGE_EVIDENCE.md). This does not establish Linux graphical desktop support.

`node tests/linux-container-smoke.mjs` built the image and completed an authenticated HTTP upload → text edit → strict-size export. The container ran as UID 1000, with a read-only root filesystem, no Linux capabilities, `no-new-privileges`, bounded memory/PIDs/CPU/tmpfs, `--network none` and deliberately invalid developer PATH. Electron was absent. Tool discovery still found the image's explicit FFmpeg/ffprobe/yt-dlp/Node paths. Authentication, unauthorized-output rejection (401), byte-range delivery and submission idempotency passed. The output was transferred out and independently probed on the Windows host: **49,104 bytes**, **1.4 seconds**, **14 video frames**, against a **60,000-byte maximum**. The rendered `linux-output.png` was inspected and visibly shows the requested text and source timing marker.

The Linux suite verifies numbered CFR/VFR/nonzero-origin/30000÷1001 NTSC frame identity, bounded frame extraction against origin-decoded PNG bytes, copy preservation, audio alignment, crop/rotation/text/captions/audio, HEVC/AV1, original-source export after proxy, progressive/cancellable 95 s waveform windows, exact-image caching, strict byte limits, argument isolation, output bounds and owned process-tree cancellation. Its resistant-descendant test verifies the delayed SIGKILL still kills the group after the direct parent exits. Injected hardware failures test permitted fallback with a real software output and strict-policy rejection; physical GPU success is not claimed. The AV1 correction test measured **90,116 → 54,103 → 43,962 bytes** against a **50,000-byte limit**, retaining all 40 video frames. A one-attempt budget fails without publishing an oversized result. The same 50,000-byte fixture is used across OSes because different SVT/font builds produce different bitstreams.

FFmpeg **9.0.1** is source-built with GCC 14.2.0 and GPL-enabled x264/x265, SVT-AV1, AOM, explicit font libraries and GnuTLS. Official source SHA-256 is `cf38e0e28c7e5605942c4a77755349b0145804a397af37eb1fb4c77cb237f635`; its PGP signature was verified against the [published release-key fingerprint](https://ffmpeg.org/download.html) `FCF986EA15E6E293A5644F10B4322F04D67658D8`. The source tarball, build configuration and resulting binary hashes remain in the image under `/usr/local/share/media-workbench`. Node 22.23.2 uses a pinned official image digest; native libraries come from dated signed Debian snapshots; yt-dlp 2026.08.19 executable hashes are pinned. This image was built locally, not signed or published.

A concrete compatibility failure changed the initial Linux tool choice: Debian FFmpeg 7.1.5 cleared frame-rate metadata after `setpts`. It wrote a zero-duration final packet, so `nb_frames` reported ten but decoding returned nine. It also made AV1 infer an impossible frame rate. Independent review reproduced the final-frame loss. A CFR conversion would violate preserved VFR timing, so the image now uses FFmpeg 9.0.1 and exact filters explicitly require `strip_fps=0`. Version 7 is not an approved exact-export toolchain. This changes the native tool version, not the proposed application architecture.

`--tmpfs /tmp` defaults require **explicit `exec`** for yt-dlp's packaged Python shared-library extraction. `noexec` failed real version execution with a library mapping error. Other restrictions remain; `/data` can be noexec. The image declares **no Docker VOLUME**: independent review found that `/data` otherwise became an unexpected writable anonymous mount even in read-only native workers. The image was rebuilt, `Config.Volumes` was verified null, and the headless smoke reran successfully with its explicit bounded `/data` tmpfs. Docker's inherited Node entrypoint also depended on PATH, so the image now invokes the absolute Node executable directly. Docker copy did not retrieve a generated tmpfs file; the smoke test now reads those exact bytes through a container process before independent host probing.

## Shared-worker isolation boundaries

The verified local headless container is not, by itself, multi-user worker isolation: all server-owned sources and credentials would otherwise share its data volume. A separate process for each job must mount only that job's individually authorized input files read-only and its own output directory read-write, with a read-only image, no Docker socket, no privileges, strict quotas, owned-process cancellation, and no network for processing. Root's `apps/server/src/worker.ts` is the server-owned executor for that boundary; its independent tests/evidence are maintained separately.

Downloader workers additionally need kernel-enforced access only to a policy-checking proxy. An internal Docker network alone is insufficient: worker access to its gateway/host and other network members must also be denied, and DNS/IPv6/redirect/nested-manifest paths must be tested. The app must never give remote requests arbitrary container flags, mount paths, networks or executable names. A Docker socket grants host-level authority and must never be exposed inside an untrusted media worker. User namespaces/rootless-engine deployment and a narrowly authorized launcher improve the service boundary; host data paths must be translated and verified on Docker Desktop, not guessed.

Shared hosting remains rejected by the local runtime smoke configuration. This document does not approve the independent downloader-egress implementation or claim hostile-media sandbox escape resistance. Linux desktop integration, ARM64, GPU passthrough, signing, external uploads and reverse-proxy/TLS deployment remain untested here.
