## Runtime boundaries

The service owns media and processing. The desktop only receives a managed path through an owner-authenticated bridge endpoint protected by a separately generated desktop secret. The endpoint leases the artifact for one hour. General renderer/native calls use opaque IDs. Native IPC rejects other web contents, subframes, and foreign origins. Renderer Node integration is disabled, navigation/new windows are restricted, and permission prompts are denied by default.

Desktop startup requires `.tools/node` or `.tools/node.exe` and the built service. It never treats Electron's embedded runtime as a yt-dlp JavaScript executable. The shell owns its child service; a second shell focuses the existing instance. Closing the last window asks the service to close through its private stdin, waits for owned process cancellation, and uses bounded process-tree termination if necessary. There is no background tray mode or implicit reuse of an unrelated service.

Executable bindings stay in the desktop user's local action file. A native file picker and confirmation choose the executable. Arguments are arrays, with only file/name/directory substitutions; shell execution is disabled. Media-type applicability is checked before invocation. Upload handoffs always require a local confirmation and report only process completion, never an upload URL or upload success. No ShareX upload was executed in verification.

## Remaining platform evidence

- Third-party chat/email compose attachment handling remains untested. The available Discord page was not used because preparing an attachment can upload data before a message is sent. Explorer verification is real, but it does not establish every target application's behavior.
- Windows native drag-out is implemented using Electron's native drag API but a receiving application has not been verified. Reveal requests are implemented; the complete user-visible reveal workflow has not been separately asserted.
- Linux desktop clipboard and drag-out are explicitly unavailable in capabilities pending tests on individual desktop environments. Linux native desktop actions, Linux desktop package execution, and Linux UI sessions are not marked passed by Windows tests.
- The ShareX command-line contract is implemented and argument-tested. Installed ShareX execution and actual upload result integration remain untested. Bindings do not fabricate completion URLs.
- Remote-server companion transfer/pairing is not enabled in the desktop shell. A remote host path cannot be handed to local native actions.
